# E4 - Repair Compilation Law (Habits and Institutionalization Are One Law)

**Source text:** THEOREMS.md §3, E4 (lines 157-177).
**Target Lean module:** `SixBirdsFoundationsV.Laws.E4RepairCompilation`.
**Grounding:** D3 supplies carried records and source classes; D4 supplies `ESystem`, `RepairMove`,
`RepairSort` (tied to FIII's P1-P5 primitives), `LawfulRepairStep` (the full gated/audited/
kernel-realized repair-step witness, not just its `realizedByKernel` field); E1 (landed, this repo)
supplies `EndogenousRepairOccurrence`, `CorePromotionGatesPass`, and `Delta` directly reused for the
"repeatedly invoked, gate-passing, obstruction reduction" clause — E4 is a genuine E1 dependent, unlike
E11/E12. FIII's vendored `TopDownChannel` and `Promotion` modules are directly reused for lawfulness
condition (i) (round-1 fix: `Promotion.promotion_gate_soundness` is an implication
`AcceptedPromotionFamily (Promote B) -> RequiredCoreGatesPass B.gates`, not a structure with a `.holds`
field — cited correctly below). D4/D6's `SameFamilySaturated`/`AcquisitionStrict` pattern (round-1 fix:
condition (iii) requires *strictness*, i.e. `¬ SameFamilySaturated`, not `SameFamilySaturated` itself
— `sameFamilySaturation` is Xi's null-case theorem, proving saturation collapses the residual, the same
polarity E6+E9 already use to REJECT saturated candidates, not accept them). The Strict-Tests paper's
memory-only comparator (condition (ii)) and FIV's F2/F9 are not vendored in this repo; E4 treats them
as certified host input, following E1/E3/E11's own precedent for unvendored content.

**E11 forward obligation — genuinely open, not discharged here.** E11 (landed) already carries a
forward interface anticipating E4, `E4CompiledInstitutionalRewrite`
(`E11InstitutionalRewrite.lean:465-481`), a structure whose `compiledRecordFor`/`holds` fields each take
a full `MatchedInstitutionalComparison`/`TopDownChannelRecord`/`InstitutionalStructuralEffect` triple —
recorded as `ForwardObligation(E4_constitutive_compilation_correspondence)`. Discharging this requires
importing E11's own institutional-comparison vocabulary and constructing a genuine bridge instance; it
is not a one-line consequence of E4's own definitions. §1 records this as an open design question for
review (build the bridge now, or defer to the combined Social Stack treatment); E4's own core theorem
does not depend on the answer either way.

## 1. Setup

Let

```text
S : ESystem FData RuleFamily ResidualFamily AuditAccessData
      InstrumentRecord LedgerEntry DefectRecord MovePayload MoveRecord AuditRecord
H : ChallengeHistory ChallengeClass SourceQuotient DeclaredFamily
      TargetReadout ObstructionWitness DefectRecord MoveRecord AuditRecord
```

be a D4 E-system with the D5/E1 challenge-history surface. E4 does not define a new repair-invocation
mechanism; it asks whether a *repeated* endogenous repair invocation can be replaced by a silent
lower-layer rewrite.

### Repeated invocation with obstruction reduction, stable audit, idempotence defect

Reuses E1's `EndogenousRepairOccurrence` directly, applied across a finite window of episodes rather
than a single one:

**Round-1 fix (dangling witnesses):** the first draft called E1's `EndogenousRepairOccurrence` with
free names `installs`/`postState`/`R_t` that were never bound anywhere. `EndogenousRepairOccurrence`'s
real signature (`E1Internalization.lean:118-140`) fixes `installs : MovePayloadInstallsRefinement
MovePayload RepairRefinement` and `postState : PostRepairStateForEpisode ...` once per repair, and
takes a per-invocation `rho_t`/`R_t` pair. Since E4 is about the *same* repair being invoked repeatedly
(not a different repair each time — that is exactly what makes idempotence-stability meaningful), the
window binds `installs`/`postState`/`R` once, shared across all invocation times:

```text
structure CompilationCandidateWindow
    (S : ESystem ...) (H : ChallengeHistory ...)
    (C : ChallengeClass)
    (installs : MovePayloadInstallsRefinement MovePayload RepairRefinement)
    (postState : PostRepairStateForEpisode S ChallengeClass SourceQuotient DeclaredFamily
      TargetReadout ObstructionWitness)
    (R : RepairRefinement) where
  episodeTimes : List Nat            -- the recurring invocation times, e.g. t_1 < t_2 < ... < t_k
  atLeastTwoInvocations : episodeTimes.length ≥ 2   -- non-vacuity: idempotence needs ≥2 to compare
  invocations : ∀ t ∈ episodeTimes, RepairTypedAuditEntry DefectRecord MoveRecord AuditRecord
  occursAtEach :
    ∀ t ∈ episodeTimes, ∀ ht : t ∈ episodeTimes,
      EndogenousRepairOccurrence S H installs postState C t (invocations t ht) R
        -- E1's own predicate, direct reuse, one genuine occurrence per invocation time,
        -- same repair R installed each time
```

**Obstruction reduction across the window (round-1 fix: genuinely strict, not just non-increasing):**
each invocation genuinely reduces `Delta` (E1's own split-pair obstruction predicate) for challenge
class `C` — every post-invocation split pair was already a pre-invocation split pair (no new
obstructions introduced), *and* a witnessed pair existed pre-invocation that is genuinely absent
post-invocation (real reduction, not merely non-increase):

```text
def ObstructionReducingAcrossWindow
    (window : CompilationCandidateWindow S H C installs postState R) : Prop :=
  ∀ t ∈ window.episodeTimes,
    (∀ x x', Delta (post-invocation quotient at t) F_C r x x' →
      Delta (pre-invocation quotient at t) F_C r x x') ∧
    (∃ x x', Delta (pre-invocation quotient at t) F_C r x x' ∧
      ¬ Delta (post-invocation quotient at t) F_C r x x')
    -- conjunction of "no new obstructions" and "a genuine witnessed reduction" —
    -- same emptiness-wrapper convention as CompiledDescent above, not literal set notation
```

**Stable audit:** every invocation's audit entry is genuinely carried with an admissible source tag
(direct reuse of the same `FineSourceTag ∈ {committed_state, audited_cell_records}` /
`generatedByS=true` / `inScope=true` discipline `EndogenousRepairOccurrence` itself already requires —
no new audit machinery).

**Idempotence defect below threshold (new vocabulary — not in any existing Lean file). Round-1 fix:**
the window's own `atLeastTwoInvocations : episodeTimes.length ≥ 2` field (added above) is what closes
the non-vacuity gap — `IdempotenceStableAcrossWindow` no longer needs its own separate guard, since no
window satisfying the type can have fewer than two invocations to compare in the first place:

```text
structure IdempotenceDefectMeasure (S : ESystem ...) where
  defect : MovePayload → MovePayload → Rat        -- exact-rational distance between repeated payloads
  defectNonneg : ∀ p p', 0 ≤ defect p p'

def IdempotenceStableAcrossWindow
    (measure : IdempotenceDefectMeasure S)
    (window : CompilationCandidateWindow S H C installs postState R)
    (threshold : Rat) : Prop :=
  ∀ t ∈ window.episodeTimes, ∀ t' ∈ window.episodeTimes,
    measure.defect (window.invocations t _).moveRecord.payload
      (window.invocations t' _).moveRecord.payload ≤ threshold
```

i.e. repeated invocations install essentially-the-same repair payload (bounded drift), which is exactly
what licenses treating the whole window as "one thing to compile," not a sequence of unrelated repairs.

### Compiled operator (P1 rewrite or P2 support gate)

D4's `RepairSort` already ties every repair move to one of FIII's P1-P5 primitive roles, and FIII's own
gloss reads P1 as "rewrite/descent" and P2 as "representability/gating/support control" — an exact,
pre-existing match for "a lower-layer operator rewrite (P1) or support gate (P2)." **Round-1 fix:** the
first draft claimed kernel realization but only stored a bare `RepairMove`; `LawfulRepairStep`'s full
field list (`ESystem.lean:123-148`: `defectCarried`, `detected`, `gateAllowed`, `admissible`,
`budgetLineInLedger`, `realizedByKernel`) requires the concrete `z z' defect auditRecord` witnesses, not
just the move itself. A compiled operator now carries the genuine step witness plus one new field this
law adds:

**Round-2 fix (unlinked evidence, closing two findings at once):** round-1's `CompilationLawful` took
`channelRecord`/`promotionData`/`memoryOnly`/the saturation witness as *separately supplied*
parameters, never tied to `candidate` — a host could satisfy "lawfulness" with an unrelated top-down
channel or an unrelated strictness witness. Mirroring E11's own anti-unlinked-evidence discipline
(store evidence *on* the record being classified, not pass it in from elsewhere), `CompiledOperatorRecord`
now carries all four certifying witnesses as its own fields, plus an explicit `forChallengeClass`/
`forRepair` tag so `CompiledOperatorRecordAttributedTo` (below) can check the candidate is genuinely
about the *same* window, not an arbitrary carried move:

```text
structure CompiledOperatorRecord
    (S : ESystem ...) (C : ChallengeClass) (R : RepairRefinement) where
  z z' : S.T.Z
  defect : DefectRecord
  move : RepairMove ...
  auditRecord : AuditRecord
  sortIsRewriteOrGate : move.sort.val = SixBirdsIII.Primitive.P1 ∨
    move.sort.val = SixBirdsIII.Primitive.P2
  lawfulStep :
    LawfulRepairStep S.Lambda_S S.defectRecordPolicy S.moveRecordPolicy S.auditRecordPolicy
      S.I_S S.AdmissibleMove z z' defect move auditRecord
      -- the genuine gated/audited/kernel-realized witness, not just realizedByKernel in isolation
  decompilationRecord : DefectRecord        -- annotation: what class this compiled a repair FOR
  annotationCarried : ∃ n, CarriedRecordAt decompilationPolicy decompilationRecord n
    FineSourceTag.committed_state true true
  -- lawfulness-certifying witnesses, now OWNED by this record (not separately supplied later)
  channelRecord : SixBirdsIII.TopDownChannelRecord
  promotionData : SixBirdsIII.PromotionBridgeData ...
  memoryOnly : MemoryOnlyComparatorCertified S C
  saturated : Family -> Probe -> Prop
  L : Family
  Mprobe : Probe
```

The `decompilationRecord`/`annotationCarried` fields are the mechanization of source-text condition
(iv) — "the compiled operator carries a decompilation/annotation record" — a genuinely new addition to
`RepairMove`'s own vocabulary (no existing structure has this), not a reuse of anything. `C`/`R` are
now type parameters of `CompiledOperatorRecord` itself (not free names) — the candidate is, by
construction, always a candidate *for* a specific class and repair, closing `CompiledOperatorRecordAttributedTo`'s
own unlinked-evidence gap below.

### Lawfulness conditions (i)-(iv)

**Round-1 fixes to both API citations (unchanged from round 1, re-verified):**
- (i)'s promotion half: `Promotion.promotion_gate_soundness` (`Promotion.lean:65-68`) is the implication
  `AcceptedPromotionFamily (Promote B) -> RequiredCoreGatesPass B.gates`, not a structure with a
  `.holds` field. `CompilationLawful` requires the *hypothesis* `AcceptedPromotionFamily (Promote
  candidate.promotionData)`; the theorem is what lets the Lean mechanization later *derive*
  `RequiredCoreGatesPass candidate.promotionData.gates` from it, not something asserted redundantly here.
- (iii): Xi's `sameFamilySaturation` (`StrictExtension.lean:51`) is the *null-case* theorem — same-
  family saturation collapses the extended residual to the original, exactly the "renaming discharges
  nothing" fact E6+E9 already use to *reject* saturated candidates via D4/D6's `AcquisitionStrict :=
  ¬ SameFamilySaturated` wrapper (`ProbeEconomy.lean:30-36`). A *lawful* compilation must therefore
  require strictness — `¬ SameFamilySaturated`, not `SameFamilySaturated` itself — mirroring E6+E9's
  own polarity exactly, not inverting it.

**Round 2:** every conjunct now reads its witness directly off `candidate`'s own fields — no separately
supplied parameter that could belong to an unrelated claim:

```text
def CompilationLawful (candidate : CompiledOperatorRecord S C R) : Prop :=
  -- (i) direct FIII reuse, both modules
  SixBirdsIII.TopDownChannelAcceptedBool candidate.channelRecord = true ∧
    candidate.channelRecord.effectGate = true ∧
    SixBirdsIII.AcceptedPromotionFamily (SixBirdsIII.Promote candidate.promotionData) ∧
      -- promotion_gate_soundness then derives RequiredCoreGatesPass from this, not re-asserted here
  -- (ii) certified host input (Strict-Tests paper content, not vendored)
  candidate.memoryOnly.survivesControl ∧
  -- (iii) strictness, not saturation — the D4/D6 AcquisitionStrict polarity, direct Xi reuse
  --       underneath it for the concrete instantiation (matching E1/E6+E9's own null-battery item 4)
  ¬ SameFamilySaturated candidate.saturated candidate.L candidate.Mprobe ∧
  -- (iv) decompilation/annotation record, defined above
  candidate.annotationCarried
```

**Design note for review:** condition (i) cites TWO distinct vendored FIII modules —
`TopDownChannel` (structural certification: ≥2 interventions, matched controls, effect threshold) and
`Promotion` (the abstract promotion-gate soundness bridge, `promotion_gate_soundness`). Both are
genuinely vendored in this repo (`lean/vendor/foundations/six-birds-foundations-iii/lean/full/SixBirdsIII/
TopDownChannel.lean` and `Promotion.lean`), so this is direct reuse of two already-proven theorems, not
a certified bridge for either — mirroring E11's own precedent for `TopDownChannel` specifically, and
extending it to `Promotion` for the first time in this repo. `PromotionBridgeData` is FIII's own
abstract record type; E4 does not yet have a concrete D4-instantiation bridge showing `S.I_S`'s
`Detects`/`GateAllows`/`ReAudits` fields genuinely populate a `PromotionBridgeData` instance — this gap
is flagged explicitly in §6 (Nonclaims), following the same honest caveat E1.md's own Interaction
Status already raises for the identical FIII `Promotion` module.

### Compiled descent and the higher package going silent

Lean's `Delta` (`E1Internalization.lean:18-21`) is a 2-argument split-pair relation
(`q x = q x' ∧ r (F_C x) ≠ r (F_C x')`), not literally a set — the source text's `Delta(Q, F_C, r) = ∅`
notation is paper shorthand for "no pair satisfies the relation." E1 already has the corresponding Lean
wrapper split, `Delta_endo`/`DeltaEndoEmpty` (`E1Internalization.lean:301`/`332`); E4 follows the exact
same split rather than writing `Delta(...) = ∅` as literal Lean:

```text
def CompiledDescent (candidate : CompiledOperatorRecord S C R) : Prop :=
  ∀ x x', ¬ Delta candidate.inducedQuotient F_C r x x'
    -- an emptiness wrapper over E1's Delta, mirroring DeltaEndoEmpty's own shape

def HigherPackageGoesSilent
    (window : CompilationCandidateWindow S H C installs postState R) (afterTime : Nat) : Prop :=
  ∀ t > afterTime, t ∉ window.episodeTimes →
    ¬ ∃ rho_t, EndogenousRepairOccurrence S H installs postState C t rho_t R
      -- no NEW endogenous invocation witnessed for this challenge class after compilation,
      -- same shared repair R as the window itself (not a dangling per-time R_t)
```

**External-review-gate addendum (v24 CHANGE-REQUEST fix): candidate-to-quotient linkage.** The first
Lean mechanization of `CompiledDescent` took the quotient as a free parameter `q`, with `candidate`
itself underscore-prefixed and unused in the body — despite this section's own pseudocode always
calling for "the quotient induced by `candidate.move`." The Lean surface had drifted from its own
six-field spec: since `Delta q F_C r x x' := q x = q x' ∧ r (F_C x) ≠ r (F_C x')`, any injective `q`
(e.g. the identity) makes `∀ x x', ¬ Delta q F_C r x x'` trivially true regardless of what the
candidate's compiled operator actually does — a host could satisfy `CompiledCase`/`E4_Compilation`
using descent evidence for a quotient with no relationship to the candidate at all. The same gap
existed in `E4_Brittleness`, whose `candidate` argument was likewise unused and whose `baseQuotient`
was a free, unlinked parameter. The fix follows this law's own established pattern (already used for
`channelRecord`/`promotionData`/`memoryOnly`/`saturated` — see the Lawfulness Conditions subsection
above): `CompiledOperatorRecord` now owns `inducedQuotient : X -> Q` as a field, and `CompiledDescent`,
`OutOfClassObstructionWitness`, `CompiledCase`, `MisCompiledCase`, `CompilingCase`, the five `...Holds`
wrappers, `E4_Compilation`, and `E4_StatusPartition` all reference `candidate.inducedQuotient` instead
of a separately-supplied `q`; `E4_Brittleness` reads `candidate.inducedQuotient` in place of the
unlinked `baseQuotient`. This closes the gap the same way the project's other certified-evidence
fixes do: by committing the quotient as part of the candidate's own identity, so a host cannot cite
descent/brittleness evidence for one quotient while classifying an unrelated candidate. The Python
toy-lab mirror (`e4_repair_compilation_sweep.py`) already had this right — `CompiledOperatorCandidate`
owns `descent_residuals`/`silent_future_invocations` as fields — so only the Lean mechanization needed
to catch up; no toy-lab or prediction changes were required (all 16 registered comparisons still PASS
with unchanged values).

**`HigherPackageGoesSilent` is deliberately left window-scoped, not candidate-scoped.** The same v24
review round separately, and less severely, noted that `HigherPackageGoesSilent` doesn't mention
`candidate` at all. This is an intentional design choice, not an oversight: silence is a fact about
the *window's shared audit trail* (no new endogenous repair occurrence for this challenge class after
`afterTime`), and the window is already tied to the specific candidate via
`CompiledOperatorRecordAttributedTo` wherever `HigherPackageGoesSilent` is used (inside `CompiledCase`/
`MisCompiledCase`/`CompilingCase`). Adding a second, candidate-owned silence witness would duplicate
that linkage rather than close a real gap, so this was left unchanged.

### E11 forward-obligation: open design question (corrected from an earlier draft mistake)

An earlier version of this section proposed treating `E4CompiledInstitutionalRewrite.holds` as a
predicate callable directly on a bare compiled record. That is wrong: `E4CompiledInstitutionalRewrite`
(`E11InstitutionalRewrite.lean:465-481`) is a *structure* with two function-valued fields,

compiledRecordFor :
  MatchedInstitutionalComparison S -> SixBirdsIII.TopDownChannelRecord ->
    InstitutionalStructuralEffect S -> CompiledRewriteRecord
holds :
  MatchedInstitutionalComparison S -> SixBirdsIII.TopDownChannelRecord ->

Genuinely discharging E11's `ForwardObligation(E4_constitutive_compilation_correspondence)` requires an
*instance* of this structure — which requires E4 to import E11's own `MatchedInstitutionalComparison`/
`TopDownChannelRecord`/`InstitutionalStructuralEffect`/`CompiledRewriteRecord` vocabulary and construct
a genuine bridge from E4's `CompiledOperatorRecord`/`CompilationLawful` world into that vocabulary — a
substantive cross-law construction, not a one-line citation.

**Open question for review:** should this bridge be built as part of *this* E4 landing, or deferred to
the combined "Social Stack" treatment THEOREMS.md itself names (E11+E4+E12+E13, §1.1)? E4's own core
theorem (`E4_Compilation`) does not need this bridge to be proven — it is self-contained over D4/E1/

here as a genuine open design question, not resolved unilaterally; §5 (Interaction Status) records

### Status apparatus (five-way, priority-normalized from the start)

Following the lesson from E12's own external-review round (a `Candidates`-style restriction applied to
only part of a priority chain caused a genuine CHANGE-REQUEST), E4's five-way partition is designed
priority-normalized *from this first draft*, not retrofitted after review.

**Round-2 fixes (three distinct bugs the reviewer caught in round-1's version):**
1. `CompiledOperatorRecordAttributedTo` didn't actually check the candidate belonged to the *given*
   window — now `CompiledOperatorRecord` itself carries `C`/`R` as type parameters (§ above), so
   attribution is a genuine equality/carriedness check, not a free-floating carried-record lookup.
2. The priority order was genuinely wrong: `MisCompiledCase`/`DecompiledCase` each negated
   `CompiledCase`, but a mis-compiled operator is *by the source text's own definition* one that
   **was** successfully compiled in-class (lawful, in-class descent, silent) and *additionally*
   accrues an out-of-class obstruction — negating `CompiledCase` made this state unreachable. The fix:
   `CompiledCase` and `MisCompiledCase` share the exact same positive core (lawful ∧ in-class descent ∧
   silent), differentiated *only* by whether a genuine out-of-class obstruction witness exists — not by
   negating each other.
3. A window whose candidate is `CompilationLawful` but (because the window's own obstruction-reduction/
   idempotence hypotheses don't hold) fails `CompiledDescent`/`HigherPackageGoesSilent` had no home in
   round-1's version. Fix: `CompilingCase` is now the genuine catch-all ("mixed," per the source text's
   own gloss) — every candidate that isn't exposed, decompiled, compiled, or mis-compiled lands there,
   by construction, mirroring E12's own `NonIndividuatedCase` catch-all discipline. `DecompiledCase` is
   promoted to priority 2 (right after `ExposedCase`): a genuine reversion event is a terminal fact
   about the candidate's history and should not be masked by whatever its lawfulness/descent status
   happened to be before reversion — a deliberate, disclosed deviation from the source text's own
   listing order, not a silent one.

```text
inductive CompilationStatus where
  | exposed         -- invoked per-episode, no compiled operator attributed yet
  | decompiled      -- a previously-compiled operator has a genuine, carried reversion event
  | compiled        -- lawful, in-class descent, silent, and NO out-of-class obstruction witness
  | mis_compiled    -- lawful, in-class descent, silent, but a genuine out-of-class obstruction exists
  | compiling       -- catch-all: attributed, not decompiled, and neither compiled nor mis-compiled

def CompiledOperatorRecordAttributedTo
    (window : CompilationCandidateWindow S H C installs postState R)
    (candidate : CompiledOperatorRecord S C R) : Prop :=
  ∃ n, CarriedRecordAt compiledPolicy candidate.move.moveRecord n
    FineSourceTag.committed_state true true
    -- genuine attribution: candidate's own C/R type parameters must match the window's C/R
    -- (enforced by construction, since candidate : CompiledOperatorRecord S C R is typed
    -- against the SAME C/R the window itself is indexed by, not merely an unconstrained lookup)

def ExposedCase
    (window : CompilationCandidateWindow S H C installs postState R) : Prop :=
  ¬ ∃ candidate, CompiledOperatorRecordAttributedTo window candidate

-- Genuine reversion witness, tied to the SAME candidate's own decompilationRecord:
structure DecompilationEventRecord
    (candidate : CompiledOperatorRecord S C R) where
  eventTime : Nat
  revertsRecord : DefectRecord
  revertsMatchesCandidate : revertsRecord = candidate.decompilationRecord
  carried : ∃ n, CarriedRecordAt decompilationEventPolicy revertsRecord n
    FineSourceTag.committed_state true true

def DecompiledCase
    (window : CompilationCandidateWindow S H C installs postState R)
    (candidate : CompiledOperatorRecord S C R) : Prop :=
  ¬ ExposedCase window ∧
    CompiledOperatorRecordAttributedTo window candidate ∧
    ∃ event : DecompilationEventRecord candidate, True

-- Carried classification of a specific out-of-class obstruction pair (closes the F9/unstatused-
-- residual falsifier's own dangling reference from round 1). Round-3 fix: concrete enum, not a bare
-- name — the two dispositions THEOREMS.md's own text anticipates for an out-of-class obstruction
-- (accept the brittleness as a known trade-off, or repair it back into the declared class):
inductive ObstructionClassification where
  | accepted_brittleness   -- the obstruction is acknowledged and accepted as compilation's known cost
  | repaired               -- a subsequent repair discharges the obstruction for this (class, pair)

structure ObstructionStatusRecord
    (candidate : CompiledOperatorRecord S C R) where
  forClass : ChallengeClass
  x x' : X
  assignedStatus : ObstructionClassification

def CarriedObstructionStatusFor
    (candidate : CompiledOperatorRecord S C R) (otherClass : ChallengeClass) (x x' : X)
    (record : ObstructionStatusRecord candidate) : Prop :=
  record.forClass = otherClass ∧ record.x = x ∧ record.x' = x' ∧
    ∃ n, CarriedRecordAt obstructionStatusPolicy record n FineSourceTag.committed_state true true

-- Genuine out-of-class-obstruction witness, tied to the SAME compiled candidate:
structure OutOfClassObstructionWitness
    (candidate : CompiledOperatorRecord S C R) where
  otherClass : ChallengeClass
  otherClassDistinct : otherClass ≠ C
  x x' : X
  obstructs : Delta (quotient induced by candidate.move) F_{otherClass} r x x'
  unstatused : ¬ ∃ record, CarriedObstructionStatusFor candidate otherClass x x' record
    -- no carried status record classifies this out-of-class obstruction — F9 violation witness

def CompiledCase
    (window : CompilationCandidateWindow S H C installs postState R)
    (candidate : CompiledOperatorRecord S C R) : Prop :=
  ¬ ExposedCase window ∧
    ¬ DecompiledCase window candidate ∧
    CompiledOperatorRecordAttributedTo window candidate ∧
    CompilationLawful candidate ∧
    CompiledDescent candidate ∧
    HigherPackageGoesSilent window afterTime ∧
    ¬ ∃ witness : OutOfClassObstructionWitness candidate, True

def MisCompiledCase
    (window : CompilationCandidateWindow S H C installs postState R)
    (candidate : CompiledOperatorRecord S C R) : Prop :=
  ¬ ExposedCase window ∧
    ¬ DecompiledCase window candidate ∧
    CompiledOperatorRecordAttributedTo window candidate ∧
    CompilationLawful candidate ∧
    CompiledDescent candidate ∧
    HigherPackageGoesSilent window afterTime ∧
    ∃ witness : OutOfClassObstructionWitness candidate, True
    -- shares CompiledCase's exact positive core; differs ONLY on the witness's existence,
    -- so CompiledCase/MisCompiledCase are exclusive by this one existential and exhaustive
    -- between themselves whenever the shared core holds

def CompilingCase
    (window : CompilationCandidateWindow S H C installs postState R)
    (candidate : CompiledOperatorRecord S C R) : Prop :=
  ¬ ExposedCase window ∧
    ¬ DecompiledCase window candidate ∧
    ¬ CompiledCase window candidate ∧
    ¬ MisCompiledCase window candidate ∧
    CompiledOperatorRecordAttributedTo window candidate
    -- the true catch-all: covers "not yet CompilationLawful", "lawful but the window's own
    -- obstruction-reduction/idempotence hypotheses don't hold so descent/silence isn't derivable",
    -- and any other attributed-but-not-yet-settled state — matching the source text's own
    -- "compiling (mixed)" gloss
```

`ExposedCase` is the only case that does not carry a distinguished `candidate` (there is none yet). The
priority order is now `exposed > decompiled > {compiled, mis_compiled} > compiling`, with `compiled`/
`mis_compiled` mutually exclusive via the `OutOfClassObstructionWitness` existential and `compiling` as
the genuine, unconditional catch-all — closing all three round-1 exhaustiveness/priority bugs.

### Carried status record and occurrence-complete classifier (round-2 addition, closing a missing-apparatus finding)

Round-1 asserted `E4_StatusPartition` follows from "an occurrence-complete carried status classifier"
without ever defining one — the reviewer correctly flagged this as inconsistent with the E1/E3/E11/E12
precedent, where a `...StatusRecord`/`...StatusOccurrenceFor`/`Complete...Status` triple is always
defined before the partition theorem is stated. E4 now follows the same triple exactly:

**Round-3 fix (candidate-linking gap):** round-2's `CompilationStatusRecord` had no field naming which
candidate it classified — a carried record could certify `status = .compiled` via an existential
candidate the record itself never mentions, and (since E4 does not claim compiled-operator uniqueness)
the partition claim needs to be *per candidate*, not a single window-level fact. The fix explicitly
threads an `Option (CompiledOperatorRecord S C R)` — `none` for the exposed case (no candidate exists
at all), `some candidate` naming exactly which attributed candidate this record classifies:

```text
structure CompilationStatusRecord
    (S : ESystem ...) (LedgerEntry : Type) (AuditRecord : Type) where
  windowRef : ChallengeClass × RepairRefinement    -- which (C, R) window this record classifies
  candidateRef : Option MoveRecord                 -- none for exposed; else the named candidate's
                                                    -- own move.moveRecord identity anchor
  status : CompilationStatus
  supportingLedgerEntries : List LedgerEntry
  supportingAuditRecords : List AuditRecord

def CompilationStatusOccurrenceFor
    (window : CompilationCandidateWindow S H C installs postState R)
    (candidateOpt : Option (CompiledOperatorRecord S C R))
    (record : CompilationStatusRecord S LedgerEntry AuditRecord) : Prop :=
  record.windowRef = (C, R) ∧
    record.candidateRef = candidateOpt.map (fun c => c.move.moveRecord) ∧
      -- anti-unlinked-evidence guard: the record's own candidateRef must match the SAME candidate
      -- (or none) being classified, not an arbitrary one
    (∃ n, CarriedRecordAt statusPolicy record n FineSourceTag.committed_state true true) ∧
    (∀ entry ∈ record.supportingLedgerEntries, entry ∈ S.Lambda_S.ledgerEntries) ∧
    ∀ auditRecord ∈ record.supportingAuditRecords,
      HasCarriedRecordEvidence S.auditRecordPolicy auditRecord

def CompleteCompilationStatus
    (window : CompilationCandidateWindow S H C installs postState R)
    (candidateOpt : Option (CompiledOperatorRecord S C R)) : Prop :=
  (∃ record, CompilationStatusOccurrenceFor window candidateOpt record ∧
    (match candidateOpt with
      | none => record.status = .exposed ∧ ExposedCase window
      | some candidate =>
          (record.status = .decompiled ∧ DecompiledCase window candidate) ∨
          (record.status = .compiled ∧ CompiledCase window candidate) ∨
          (record.status = .mis_compiled ∧ MisCompiledCase window candidate) ∨
          (record.status = .compiling ∧ CompilingCase window candidate))) ∧
    ∀ record1 record2,
      CompilationStatusOccurrenceFor window candidateOpt record1 →
      CompilationStatusOccurrenceFor window candidateOpt record2 →
      record1.status = record2.status
```

The partition is now stated **per `(window, candidateOpt)`**, not per window alone: `candidateOpt =
none` is the only way to reach `exposed` (and `ExposedCase window`'s own definition already forces
this to be the unique candidateOpt possible when no candidate is attributed at all), while each
attributed candidate gets its own independent, fully-determined status among the remaining four cases
— consistent with E4 never claiming compiled-operator uniqueness for a window.

Same shape as E12's `IndividuationStatusRecord`/`IndividuationStatusOccurrenceFor`/
`CompleteIndividuationStatus` triple — one branch-valid carried record plus status uniqueness across
all genuine occurrences for the same window.

**Round-5 addition (missing `...Holds` wrappers):** matching E12's own `IntegratedHolds`/`FederatedHolds`/
etc. pattern (omitted from earlier rounds — an oversight caught during a final fresh read, not a
reviewer finding this round, but fixed now rather than left for a sixth round):

**Round-6 fix:** the first draft of these wrappers omitted the corresponding case predicate as a
conjunct — a real gap (caught by review, not by me first this time): as stated, `CompiledHolds` could
hold from a carried record merely *tagged* `.compiled`, even if `CompiledCase` were false, making the
theorem far weaker than intended. E12's own `IntegratedHolds`/etc. always include the occurrence, the
status tag, *and* the case predicate as three separate conjuncts — matched here exactly:

```text
def ExposedHolds (window : CompilationCandidateWindow S H C installs postState R) : Prop :=
  ∃ record, CompilationStatusOccurrenceFor window none record ∧
    record.status = .exposed ∧ ExposedCase window

def DecompiledHolds
    (window : CompilationCandidateWindow S H C installs postState R)
    (candidate : CompiledOperatorRecord S C R) : Prop :=
  ∃ record, CompilationStatusOccurrenceFor window (some candidate) record ∧
    record.status = .decompiled ∧ DecompiledCase window candidate

def CompiledHolds
    (window : CompilationCandidateWindow S H C installs postState R)
    (candidate : CompiledOperatorRecord S C R) : Prop :=
  ∃ record, CompilationStatusOccurrenceFor window (some candidate) record ∧
    record.status = .compiled ∧ CompiledCase window candidate

def MisCompiledHolds
    (window : CompilationCandidateWindow S H C installs postState R)
    (candidate : CompiledOperatorRecord S C R) : Prop :=
  ∃ record, CompilationStatusOccurrenceFor window (some candidate) record ∧
    record.status = .mis_compiled ∧ MisCompiledCase window candidate

def CompilingHolds
    (window : CompilationCandidateWindow S H C installs postState R)
    (candidate : CompiledOperatorRecord S C R) : Prop :=
  ∃ record, CompilationStatusOccurrenceFor window (some candidate) record ∧
    record.status = .compiling ∧ CompilingCase window candidate
```

## 2. Theorem

**`E4_Compilation`** (round-5 fix: a deeper issue than round-4's — `CompiledDescent`/
`HigherPackageGoesSilent` cannot be *derived* from `CompilationLawful` plus the window's own
obstruction-reducing/idempotence history at all. `CompilationLawful`'s four conditions are
*certification* gates (is this a genuine, non-smuggled, non-memory-only, non-renamed compilation with
a decompilation record?) — they say nothing about whether `candidate.move`'s own induced quotient
actually achieves empty `Delta` or actually silences future invocations. Nothing in D4/E1/FIII/Xi
bridges "the window's invocation history improved" to "this specific candidate's move achieves full
descent." Following this project's established verification-shaped house style (E1/E3/E11/E12 all take
a case predicate's full conjunct list as *given, independently-verified* facts — never derived from
weaker premises — before concluding the corresponding `...Holds` existence claim), `E4_Compilation` is
restated honestly: it takes `CompiledCase` itself as its hypothesis (not something to derive), and
concludes `CompiledHolds`):

Given a `CompilationCandidateWindow` with `ObstructionReducingAcrossWindow`, stable audit, and
`IdempotenceStableAcrossWindow` below a declared threshold (establishing this is a genuine,
repeatedly-invoked, converging repair worth attempting to compile — the source text's own scope
condition, not a premise from which descent/silence follow), if a `CompiledOperatorRecord` is
attributed to the window, is `CompilationLawful` (certified per conditions i-iv), and
`CompiledDescent`/`HigherPackageGoesSilent` are **independently verified** to hold for that specific
candidate (checked directly — in the toy-lab, by literally computing the candidate's induced quotient's
`Delta`-emptiness and confirming no new invocation records, not inferred from the window's own history)
with no genuine `DecompilationEventRecord` and no genuine `OutOfClassObstructionWitness`, then
`CompiledHolds` — a genuine carried `CompilationStatusRecord` witnesses status `compiled` for
`(window, some candidate)`. This is the `CompiledCase → CompiledHolds` instance of
`E4_StatusPartition`, not an independent existence proof that a lawful compilation always achieves
descent — the source text's own "there exists an admissible compilation such that..." existence claim
is about the toy-lab's own constructive witness (Round B exhibits one), not a general derivation this
Lean theorem proves from first principles.

**`E4_Brittleness`** (the source text's own "brittleness converse"): for a compiled operator, and a
challenge outside the declared class `C`, the compiled gate contributes a split-pair obstruction that
the *uncompiled* repair would have avoided. **Scope-honest statement**: this direction is stated
*conditional on* certified F2 (descent-repair normal form) host input, since F2 is not vendored in this
repo (no FIV Lean directory exists to import from) — following E1/E3's own precedent for unvendored
FIV citations. This is *not* a full first-principles proof of the source text's own "should follow from
F2" risk note; it is the honest, certified-input-conditional form. Concrete interface shape (round-1
addition, addressing the reviewer's request for more than a bare name):

```text
structure F2Certified
    {X : Type u} {Q : Type v} {FOut : Type w} {Readout : Type x} where
  splitObs : (X -> Q) -> (X -> FOut) -> (FOut -> Readout) -> X -> X -> Prop
  descentIffSplitObsEmpty :
    ∀ (q : X -> Q) (F : X -> FOut) (r : FOut -> Readout),
      (∀ x x', ¬ splitObs q F r x x') ↔ (descends q F r)   -- certified F2 content, not re-derived
  minimalGeneratedQuotient :
    (X -> Q) -> (X -> FOut) -> (FOut -> Readout) -> (X -> Q)  -- the generated quotient R_F
```

`E4_Brittleness` takes an `F2Certified` instance as an explicit hypothesis and applies
`minimalGeneratedQuotient`/`descentIffSplitObsEmpty` to the compiled gate under a declared out-of-class
challenge, deriving that the compiled quotient (fixed at compile time, in-class only) fails
`descends` for the out-of-class family — the brittleness split-pair obstruction the uncompiled,
per-episode repair would have avoided by re-deriving its own quotient fresh each episode.

**`E4_StatusPartition`** (round-3 fix: stated per `(window, candidateOpt)`, not per window alone, since
E4 never claims compiled-operator uniqueness): given `CompleteCompilationStatus window candidateOpt`
(the carried `CompilationStatusRecord`/`CompilationStatusOccurrenceFor` triple defined in §1, now
explicitly candidate-linked via `candidateRef`), exactly one status holds for that specific
`(window, candidateOpt)` pair — when `candidateOpt = none`, only `ExposedCase window` can hold (no
candidate exists to satisfy any of the other four); when `candidateOpt = some candidate`, exactly one
of `DecompiledCase`/`CompiledCase`/`MisCompiledCase`/`CompilingCase` holds for that candidate —
exclusivity from the priority-normalized negation chain (`decompiled > {compiled, mis_compiled} >
compiling`), exhaustiveness from `CompilingCase`'s own catch-all definition. Different candidates
attributed to the same window may independently hold different statuses; the theorem does not collapse
them into one window-level verdict. Same verification-shaped pattern as E1/E3/E11/E12's own
status-partition theorems.

### Obstruction/falsifier set

- **`Δ_compile`** (memory-only defeat): futures in `C` that descend under the memory-only comparator
  alone (no genuine repair structure needed) — defeats the compilation claim, since it shows the
  descent was "just memory," not a genuine kernel rewrite.
- **`Δ_compile`** (unstatused out-of-class obstruction): an out-of-class obstruction accrues but is
  never assigned a carried status — violates certified F9 (no unstatused residual) host input.

## 3. Proof Spine

1. Fix `S`, `H`, challenge class `C`, and a `CompilationCandidateWindow`.
2. Establish `ObstructionReducingAcrossWindow` from E1's own `Delta`/`EndogenousRepairOccurrence`
   machinery at each invocation time — direct reuse, no new obstruction-comparison machinery.
3. Establish `IdempotenceStableAcrossWindow` from the new `IdempotenceDefectMeasure`, requiring a
   genuine witnessed measure (non-vacuity: at least two invocations to compare, matching the house
   discipline of non-vacuous closure/comparison predicates established across E1/E3/E11/E12).
4. Attribute a `CompiledOperatorRecord` to the window, fixing its `sort` to P1 or P2 and constructing
   its `decompilationRecord`/`annotationCarried` fields.
5. Certify `CompilationLawful`'s four conjuncts: (i) direct citation of FIII `TopDownChannelAcceptedBool`
   and `AcceptedPromotionFamily`; (ii) certified `MemoryOnlyComparatorCertified` host input;
   (iii) `¬ SameFamilySaturated`, the D4/D6 strictness wrapper (Xi's `sameFamilySaturation` is its
   concrete null-case instantiation, cited to justify why saturation must be excluded, not required);
   (iv) the carried decompilation record.
6. **Round-5 fix:** take `CompiledDescent`/`HigherPackageGoesSilent` as independently-verified
   hypotheses about the specific candidate (not derived from `CompilationLawful` plus the window's own
   history — nothing in D4/E1/FIII/Xi bridges "the window's invocations improved" to "this candidate's
   move achieves full descent"), alongside the "clean case" hypotheses (no decompilation event, no
   out-of-class obstruction witness) that place the conclusion in `CompiledCase` specifically rather
   than `DecompiledCase`/`MisCompiledCase`. Conclude `CompiledHolds` via a genuine carried
   `CompilationStatusRecord`.
7. Record E11's forward obligation as an open design question (§1) — whether the
   `E4CompiledInstitutionalRewrite` bridge is built now or deferred to the combined Social Stack
   treatment — rather than asserting a one-line discharge; E4's own core theorem does not depend on
   the answer.
8. State `E4_Brittleness` conditional on certified F2 host input, applied to the compiled gate under a
   declared out-of-class challenge.
9. Case-split the five-way priority-normalized partition (`exposed > decompiled > {compiled,
   mis_compiled} > compiling`, `compiled`/`mis_compiled` split by the `OutOfClassObstructionWitness`
   existential rather than negating each other), from a genuine `CompleteCompilationStatus` occurrence
   witness (§1), deriving `E4_StatusPartition`.
10. State the obstruction/falsifier set as the direct contrapositives of steps 5(ii) (memory-only) and
    the certified F9 host input (unstatused out-of-class residual).

## 4. Case Enumeration

Listed in the (round-2-corrected) priority order `exposed > decompiled > {compiled, mis_compiled} >
compiling`:

1. `exposed`: no compiled operator attributed yet — every invocation still goes through the full
   per-episode endogenous repair path.
2. `decompiled`: a previously-compiled operator has a genuine, carried `DecompilationEventRecord`
   witnessing the reversal — the recognized instance of institutions being un-wound (deregulation,
   habit-breaking). Priority 2, ahead of compiled/mis-compiled/compiling: a reversion is a terminal
   fact about the candidate's history, not something a prior lawful/descending status should mask.
3. `compiled`: all four lawfulness conditions hold, in-class descent is empty, the higher package has
   gone silent, and NO genuine out-of-class obstruction witness exists — the clean
   habit/institutionalization instance.
4. `mis_compiled`: the exact same positive core as `compiled` (lawful, in-class descent, silent), but a
   genuine `OutOfClassObstructionWitness` DOES exist — the brittleness recognized instance (skill
   acquisition failing out-of-distribution; a standardized contract failing under an unanticipated
   dispute type). Mutually exclusive with `compiled` by the witness's existence/non-existence, not by
   negating each other's other conjuncts.
5. `compiling`: the genuine catch-all — attributed, not decompiled, and satisfying neither `compiled`
   nor `mis_compiled`'s shared core (e.g. not yet `CompilationLawful`, or lawful but the window's own
   obstruction-reduction/idempotence hypotheses don't hold so descent/silence isn't derivable yet).
6. Edge case: a candidate satisfying (i)/(iii)/(iv) but failing (ii) — the memory-only comparator
   reproduces the descent — must fail `CompilationLawful` and therefore land in `compiling`, never
   `compiled`/`mis_compiled`, flagged via `Δ_compile`.
7. Edge case: a compiled operator whose `sort` is neither P1 nor P2 — must fail
   `sortIsRewriteOrGate` and therefore never construct a valid `CompiledOperatorRecord` at all.
8. Edge case: same-family renaming (a repair repackaged under a new payload label with no genuine
   structural change) — must satisfy `SameFamilySaturated` (Xi's `sameFamilySaturation` witnesses the
   collapse), hence fail `¬ SameFamilySaturated` and therefore fail `CompilationLawful`.
9. Edge case (falsifier, unstatused residual): an out-of-class obstruction exists but no carried status
   record assigns it a class — this is exactly `OutOfClassObstructionWitness`'s own `unstatused`
   conjunct, and must route the candidate to `mis_compiled`, not `compiled`.
10. Edge case: `IdempotenceStableAcrossWindow` computed from a single invocation (vacuous "stability")
    — blocked structurally by the window's own `atLeastTwoInvocations` field, not by a separate guard.
11. Edge case: a candidate that is both lawful-with-descent-and-silence AND has a genuine
    `DecompilationEventRecord` — must land in `decompiled`, not `compiled`/`mis_compiled`, confirming
    the priority-2 placement is load-bearing (this is exactly the scenario round-1's version got wrong
    by negating `CompiledCase` inside `DecompiledCase` instead of the reverse).
