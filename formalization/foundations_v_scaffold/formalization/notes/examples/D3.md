# D3 - Carried Record And Carried Instrument

**Source text:** THEOREMS.md §1.2, D3.  
**Target Lean module:** `SixBirdsFoundationsV.Definitional.CarriedRecord`.  
**Grounding:** Foundations III §4.8.1 supplies the paper-side fine `SourceOfTruth` family and source-record discipline. The vendored FIII Lean supplies coarse `SourceTag`, `VisibilityTag`, `ThresholdTag`, `AuditTag`, `Instrument`, and record structures, but not the fine source split D3 needs.

## 1. Setup

D3 separates system-carried records from observer annotations. The definition has three independent layers of data.

### Carrier and transition data

Let `S` be a system with carrier state type `Z`. The carrier is the state space whose coordinates are updated by the system's own dynamics. Write the system's transition support abstractly as

```text
suppK : Z -> Z -> Prop
```

or, in a stochastic host, as the positive-support relation of a kernel `K`. Carriedness is asserted relative to a declared trajectory under a declared scope, not relative to every conceivable history. D3 does not require a specific Foundations I carrier type. It only needs the parametric data:

```text
Z                 carrier state type
rhoOf : Z -> R    record readout / coordinate projection
suppK             own transition support
tau               declared trace / history of carrier states
nStart            certified start index for the declared run segment
n0                point of interest in the trace
```

The trace may be represented as a finite list of states, a bounded finite sequence, or a scoped stream

```text
tau : Nat -> Z
StepInScope : Nat -> Prop
LegitimateStart(tau, nStart)
```

with a declared contiguous support witness:

```text
nStart <= n0
and LegitimateStart(tau, nStart)
and forall n,
  (nStart <= n and n < n0) ->
    StepInScope n and suppK (tau n) (tau (n+1)).
```

The record value being classified must be the value actually read on this declared trace:

```text
rho = rhoOf (tau n0)
```

for an index `n0` inside the declared scope.

The contiguity requirement is load-bearing. `StepInScope` is not an arbitrary subset of convenient steps; it must hold for every index in the interval from the certified start up to the point where `rho` is read.

The phrase "rho is part of the carrier state" means more than "rho can be computed by the theorist." It requires a declared coordinate witness: either `Z` is explicitly decomposed with an `R` coordinate, or the system's carrier specification declares `rhoOf` as one of its state coordinates. A side table maintained by the theorist is not a coordinate of `Z`.

The phrase "updated by S's own transition kernel" means record changes in the declared trace occur only along steps witnessed by `suppK`. In a deterministic setting this can be an update map `step : Z -> Z`; in a stochastic setting it is the support of a kernel. D3 is agnostic between those hosts.

### Source-record data

The FIII paper's fine source family is:

```text
committed_state
audited_cell_records
independent_pair_witness
simulation_trace
ablation_record
fallback
unknown
contradictory
```

The first five are candidate source-of-truth tags under the surrounding `SourcePolicy_I`; `fallback` supports at most provisional acceptance unless upgraded; `unknown` and `contradictory` do not supply a full source-of-truth record.

D3 intentionally admits only two fine tags for carried records:

```text
committed_state
audited_cell_records
```

and only when the source trace is generated by `S`'s own trajectory under the declared scope. The other three paper-side candidate-real tags are not enough for D3:

```text
independent_pair_witness
simulation_trace
ablation_record
```

They may support other FIII judgments, but they do not by themselves show that the record is carried by `S`.

The vendored FIII Lean currently has only:

```lean
inductive SourceTag where
  | real
  | fallback
  | dirty
  | proxy
  | missing
```

This is coarser than the FIII paper. `SourceTag.real` merges at least the five paper-side candidate-real tags, so it cannot distinguish `committed_state` and `audited_cell_records` from `independent_pair_witness`, `simulation_trace`, and `ablation_record`. A Lean proof using only `SourceTag.real` would be a narrowed or over-approximating surrogate, not the literal D3 predicate.

### Instrument records

The vendored FIII Lean supplies:

```lean
VisibilityTag  -- visible / suppressed / outside / unknown
ThresholdTag   -- exactZero / nonzero / atMostTolerance / ... / source / bridge / audit / visibility
AuditTag       -- passes / missing / failed / sourceFailure / ...
Instrument     -- host, level, canBridgeSuppressed, auditRequired
```

It also supplies record structures such as `DefectRecord`, `ClaimRecord`, and `PairObservableRecord` that carry visibility, threshold, source, and audit fields.

For D3, "check-rule records" should be read as the carried audit/check-policy records by which the instrument evaluates visibility, thresholds, and claims. In the current vendored Lean, the closest concrete hook is `AuditTag` plus the instrument's `auditRequired` field and the relevant record fields. There is no dedicated `CheckRuleTag` structure yet; the later Lean unit should either introduce a small D3-local check-rule record type or explicitly document that it is using the current `AuditTag`/`auditRequired` surface as a narrower anchor.

## 2. Definition

### Fine source tags

For the literal D3 definition, use a fine source type matching the paper:

```text
FineSourceTag =
  committed_state
  | audited_cell_records
  | independent_pair_witness
  | simulation_trace
  | ablation_record
  | fallback
  | unknown
  | contradictory
```

Define:

```text
CarriedSource(tag, generated_by_S, in_scope)
```

to hold exactly when:

```text
(tag = committed_state or tag = audited_cell_records)
and generated_by_S = true
and in_scope = true.
```

The source condition rejects `fallback`, `unknown`, `contradictory`, theorist edits, and the other candidate-real tags unless some later definition separately upgrades them into committed state or audited cell records generated by `S`.

Here `in_scope` certifies that the source classification is within the declared scope. It is not, by itself, an endpoint-scope certificate for the read point `n0`; endpoint validity belongs to the declared trajectory certificate/host scope data, while D3 binds the record value to `rhoOf (tau n0)` and checks the contiguous support segment up to that point.

### Carried record

A record `rho` of type `R` is carried by system `S` when all three conditions hold:

1. **Carrier-coordinate condition:** `rho` is a declared coordinate of `Z`, represented by a carrier readout

   ```text
   rhoOf : Z -> R
   ```

   with a witness that `rhoOf` belongs to the system's state-coordinate specification, not to an external notebook.

2. **Endogenous-update condition:** the record is bound to a declared contiguous trajectory segment of `S`, and updates in that segment are witnessed by `S`'s own transition support. In relation form, for the declared trace `tau`, certified start `nStart`, point of interest `n0`, and scope predicate `StepInScope`,

   ```text
   nStart <= n0
   and LegitimateStart(tau, nStart)
   and forall n,
     (nStart <= n and n < n0) ->
       StepInScope n and suppK (tau n) (tau (n+1)).
   ```

   Moreover, the record being classified is the value at the point of interest:

   ```text
   rho = rhoOf (tau n0).
   ```

   Equivalently, every update event in the contiguous declared run segment that changes `rhoOf`'s value,

   ```text
   rhoOf (tau n) != rhoOf (tau (n+1)),
   ```

   is a required in-scope `suppK`-witnessed step. There is no accepted step in the segment from `nStart` to `n0` where the record value changes without a support witness, and `StepInScope` cannot be gerrymandered to skip a tainting step inside that interval. No theorist edit or external annotation may be counted as the updating move.

3. **Fine source condition:** the source record satisfies `CarriedSource`: its fine tag is `committed_state` or `audited_cell_records`, its trace is generated by `S`'s own trajectory, and the trace lies within the declared scope.

Thus:

```text
CarriedRecord(S, rho) :=
  IsCarrierCoordinate(S, rhoOf)
  and ExistsDeclaredTrajectory(S, tau, StepInScope, nStart, n0)
  and rho = rhoOf (tau n0)
  and OwnKernelTraceTo(S, suppK, tau, StepInScope, nStart, n0)
  and CarriedSource(sourceTag rho, generated_by_S rho, in_scope rho).
```

The clauses are independent. A coordinate with a fallback source is not carried. A committed-state source kept outside the carrier is not carried. A coordinate whose declared trace includes an external edit not witnessed by `suppK` is not carried.

### Carried instrument

A carried instrument `I_S` is an FIII instrument whose relevant records are carried by `S`.

Concretely, for an instrument in the FIII sense, every record used by its:

```text
visibility checks
threshold checks
audit / check-rule policy
```

must satisfy `CarriedRecord(S, -)`, and the listed records must come with a certified completeness witness saying that these lists really are the complete visibility, threshold, and audit/check-rule record inventory used by the instrument. This mirrors the `LegitimateStart` treatment for trajectories: D3 does not derive completeness internally, but it refuses to call the instrument carried unless the completeness certificate is supplied.

In a Lean formalization this should be represented by fields such as:

```text
recordsAreCompleteInventory : Prop
visibilityRecords : List Record
thresholdRecords  : List Record
checkRuleRecords  : List Record
records_complete : recordsAreCompleteInventory
all_visibility_carried : all records in visibilityRecords are carried
all_threshold_carried  : all records in thresholdRecords are carried
all_check_rules_carried : all records in checkRuleRecords are carried
```

The existing FIII `Instrument` fields (`host`, `level`, `canBridgeSuppressed`, `auditRequired`) specify the instrument's status surface. D3 adds a Foundations-V-local carrier condition on the records the instrument uses.

Minimal later-Lean declarations should therefore separate:

- a fine D3 source-tag type or refinement of FIII source records;
- a carrier-coordinate predicate;
- a contiguous own-kernel trace predicate `OwnKernelTraceTo` parameterized by `suppK`, `tau`, `StepInScope`, `nStart`, and `n0`;
- `CarriedRecord` as the conjunction of the three conditions;
- `CarriedInstrument` as "FIII instrument plus certified-complete visibility/threshold/check-rule record lists, all carried."

## 3. Proof Spine

D3 is a definition, so the proof obligations are well-definedness, decidability under finite data, and correct exclusion of non-carried sources.

### What is straightforward

Given finite decidable data:

```text
DecidableEq FineSourceTag
decidable carrier-coordinate membership
decidable suppK
decidable LegitimateStart
finite declared trace, or decidable bounded StepInScope
decidable generated_by_S and in_scope flags
```

`CarriedSource` is decidable by case analysis on the fine source tag. `OwnKernelTraceTo` is decidable for a finite trace, or for finite `Nat` bounds `nStart <= n < n0`, by checking every index in the contiguous range against both `StepInScope` and `suppK`. `CarriedRecord` is decidable as a finite conjunction. `CarriedInstrument` is decidable for finite record lists by checking the carried predicate on each listed record, provided the record-inventory completeness certificate is itself a decidable input.

The source exclusions are immediate from the definition:

- `fallback`, `unknown`, and `contradictory` are never carried sources.
- `independent_pair_witness`, `simulation_trace`, and `ablation_record` are not D3-carried merely because they are paper-side candidate source-of-truth tags.
- `SourceTag.real` from vendored Lean is insufficient to prove D3-carried, because it does not identify which fine real subtype is present.
- A coordinate edited externally is excluded directly: the declared contiguous segment would contain an update event changing `rhoOf` without a `suppK` witness, violating `OwnKernelTraceTo`. Marking that index out of `StepInScope` no longer helps, because `StepInScope` is required throughout the whole interval from `nStart` to `n0`.

The carried-instrument clause is also direct: if each visibility, threshold, and check-rule record is carried, then the instrument is carried; if any required record fails one of the three carried-record clauses, the instrument is not carried.

### What is not yet in the vendored Lean

The literal D3 source predicate cannot be expressed using only FIII's current vendored `SourceTag`. The later Lean unit must either:

1. introduce a Foundations-V-local `FineSourceTag` matching the FIII paper and map it down to coarse `SourceTag.real` only as a forgetful projection; or
2. explicitly formalize only a weaker coarse predicate, such as "coarse-real source", and label it a narrowed surrogate rather than D3 itself.

Option 1 is the faithful target.

D3's own-kernel clause can be stated parametrically over `suppK : Z -> Z -> Prop`. It does not require vendoring Foundations I / ClosureLadder now. The separate `ClosureLadder` project is Mathlib-based and currently supplies closure operators, idempotent endomaps, and packaging/repackaging facts, not a ready-made transition-kernel support API. For D3, a parametric kernel-support relation is the smaller and more faithful Lean target.

ClosureLadder vendoring may become relevant later for D4's formed package or D5/D6 closure operators, but D3's carrier/update condition does not force that dependency.

## 4. Case Enumeration

- **Committed state coordinate:** a record stored as a coordinate of `Z`, updated along `suppK`, with fine source tag `committed_state` generated by `S` under scope is carried.
- **Audited cell records:** audit records stored in the carrier and updated by the system's audit transition, with fine tag `audited_cell_records`, are carried.
- **Independent pair witness:** a record with fine tag `independent_pair_witness` may support an FIII pair-observable judgment, but it is not D3-carried unless separately installed as committed state or audited cell records generated by `S`.
- **Simulation trace:** a simulation trace is not carried by the simulated system merely because the theorist generated it. It is carried only if the trace fields are coordinates of the system being analyzed and updated by that system's own kernel.
- **Ablation record:** an ablation record is not carried by `S` merely because an experimenter produced it. It may be carried by a meta-system whose carrier includes the ablation ledger and whose kernel updates it.
- **Fallback source:** fallback is never carried for D3. It may support provisional acceptance elsewhere in FIII, but not a carried-record claim.
- **Unknown or contradictory source:** not carried; these tags supply no full source-of-truth record.
- **Theorist annotation:** a note written outside `Z`, even if correct, is not carried.
- **Coordinate but external edit:** a field in `Z` that is overwritten by an external intervention rather than by `suppK` fails directly: if the edit occurs at some `k` with `nStart <= k < n0`, the contiguous-run condition requires both `StepInScope k` and `suppK (tau k) (tau (k+1))`. Gerrymandering `StepInScope k` to false now breaks `OwnKernelTraceTo` instead of hiding the taint.
- **Coarse Lean `SourceTag.real`:** insufficient by itself. It may hide one of the three non-D3 real tags.
- **Carried instrument:** an FIII instrument whose certified-complete visibility, threshold, and check-rule record inventory is all carried is carried. If the inventory completeness certificate is missing, or if any required record is fallback, external, out-of-scope, or not kernel-updated, the instrument is not carried.

## 5. Interaction Status

D3 is not just a restatement of FIII's source-record apparatus. FIII supplies the source tags, policies, and instrument status surface. D3 adds a Foundations-V-local carrier/internality test: the record must be a state coordinate, updated by the system's own kernel, and sourced specifically as `committed_state` or `audited_cell_records` generated by the system.

This is the formal answer to THEOREMS.md's hard problem: distinguishing observer-added from system-carried refinement is not a philosophical judgment. It is a source-of-truth and carrier-update classification.

D3 interacts with FIV F2 because source-refinement repairs need provenance. F2 says that source refinement is one normal-form repair path; D3 determines whether the repair package is carried by the system or supplied by the observer. A repair package can be mathematically valid but still fail the carried-source test.

D3 interacts with D1 because a repair move `Q |-> Q vee R` does not by itself say whether `R` is system-carried. D3 classifies the source of `R`.

D3 interacts with D2 because a surplus baseline or surplus-discharge claim can be credited to the system only when the relevant record, baseline, or repair ledger is carried. Otherwise it is a theorist-side comparison.

D3 interacts with FIII instruments by adding a carried-record requirement to the visibility, threshold, and audit/check-rule records the instrument uses. The FIII `Instrument` structure remains the imported status apparatus; D3 says when such an instrument is internal to the system.

Under the anti-reductionism discipline, D3 maps and audits the source boundary. It does not reduce carriedness to generic truth, correctness, or usefulness of a record.

## 6. Nonclaims

- D3 does not assert that every FIII candidate source-of-truth tag is carried. It admits only `committed_state` and `audited_cell_records` generated by `S` under scope.
- D3 does not assert that vendored Lean `SourceTag.real` is enough for carriedness. The fine split is required for the literal definition.
- D3 does not reject theorist annotations as false or useless. It says they are not carried by `S`.
- D3 does not assert that every valid repair package, surplus ledger, or audit record is system-carried.
- D3 asserts carriedness relative to the declared trajectory and scope. It is not an unbounded claim over all conceivable histories; D5's closed-loop scope is the later definition that audits closure of all repair sources in a declared challenge history.
- D3 does not require vendoring Foundations I / ClosureLadder for its own Lean anchor; the kernel-support clause can be parameterized. Later definitions may revisit ClosureLadder for formed packages or closure operators.
- D3 does not define a full stochastic kernel implementation or support extractor. It assumes a declared `suppK` or update relation.
- D3 does not claim every FIII instrument is a carried instrument. The instrument's own records must be carried, and the visibility/threshold/check-rule lists must be certified as the complete inventory used by that instrument.
- D3 does not prove that a carried-instrument record inventory is honestly complete. Completeness is a certified input, like `LegitimateStart` for trajectories; without that input, empty or cherry-picked record lists do not establish carriedness.
- D3 does not introduce biological or life-sciences content.
