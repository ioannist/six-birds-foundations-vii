# D5 - Closed-Loop Scope

**Source text:** THEOREMS.md §1.2, D5.  
**Target Lean module:** `SixBirdsFoundationsV.Definitional.ClosedLoopScope`.  
**Grounding:** D1 supplies the repair-join operation for source refinements, D3 supplies `CarriedRecord` / `CarriedSource`, D4 supplies `ESystem`, `TheoryPackage`, fixed record policies, and `ESystem.RepairStep`, and FIV F2 supplies the split-pair obstruction apparatus that THEOREMS.md uses for challenge episodes.

## 1. Setup

D5 is a scope predicate for a D4 E-system and a declared history. It is not a freestanding law about all possible repairs, and it is not a new source-of-truth classifier.

### D4 carrier and audit surface

Let

```text
S : ESystem ...
T := S.T
```

where `T = (Z, f, Sigma_f, E, A)` is the formed package component of D4. In D4, `A` is the abstract access/audit apparatus of the formed package, and `T` also carries the shared declared trajectory data:

```text
T.Z
T.suppK
T.LegitimateStart
T.tau
T.StepInScope
T.nStart
```

D5 should build directly on this data. "T's audit" means the audit/access component `A` of the D4 `TheoryPackage`, together with the D4 active instrument and ledger records that write into that audit surface. Since `A` is intentionally abstract in D4, D5 should not inspect a concrete audit implementation. Instead, it should require a declared challenge/audit history whose completeness is certified by the host.

### Challenge episodes

THEOREMS.md does not define a separate primitive named "challenge." The recurring formal handle is FIV's split-pair obstruction. FIV Definition `def:split-pair` defines

```text
Delta(q, F, r) = {(x, x') | q x = q x' and r(F x) != r(F x')}.
```

FIV Theorem `thm:F2` says that `r o F` descends through `q` iff this obstruction is empty; when it is nonempty, the canonical repairs are source refinement and target coarsening. D1 makes the source-refinement notation lawful as

```text
Q |-> Q vee R.
```

For D5, a challenge episode should therefore be represented as declared F2-style data, not as a new kind of object:

```text
ChallengeEpisode :=
  time index n along T.tau
  challenge class C
  source quotient q_n
  declared family/readout F_C
  target readout r_C
  optional obstruction witness Delta(q_n, F_C, r_C) != empty
```

The obstruction witness is optional at D5 level because closed-loop scope is about source admissibility of repair records, not about whether the challenge binds. E1 adds positive-density recurrence and nonempty obstruction hypotheses.

### Repair-typed audit records

D4 already identifies the repair-loop record families:

```text
DefectRecord
MoveRecord
AuditRecord
```

and fixes one D3 carried-record policy for each:

```text
S.defectRecordPolicy
S.moveRecordPolicy
S.auditRecordPolicy
```

D5 should use these families directly, but it must not check only the bare record value. A repair record enters an audit by a specific classified path: the audit records a read-off time and source classification for that particular occurrence. Two equal-valued records can enter by different paths, for example one committed by the system and one fallback-supplied by a theorist. D5 must classify the audit occurrence, not merely the value.

A later Lean target can use a small wrapped entry type such as:

```text
RepairEntryClass :=
  n0 : Nat
  sourceTag : FineSourceTag
  generatedByS : Bool
  inScope : Bool

RepairTypedAuditEntry :=
  defect(d : DefectRecord, c : RepairEntryClass)
  | move(m : MoveRecord, c : RepairEntryClass)
  | audit(a : AuditRecord, c : RepairEntryClass)
```

with a dispatching carriedness predicate that uses D4's explicit `CarriedRecordAt`, not the existential `HasCarriedRecordEvidence`:

```text
RepairTypedAuditEntryCarried(S, defect d c) :=
  CarriedRecordAt S.defectRecordPolicy d c.n0 c.sourceTag c.generatedByS c.inScope

RepairTypedAuditEntryCarried(S, move m c) :=
  CarriedRecordAt S.moveRecordPolicy m c.n0 c.sourceTag c.generatedByS c.inScope

RepairTypedAuditEntryCarried(S, audit a c) :=
  CarriedRecordAt S.auditRecordPolicy a c.n0 c.sourceTag c.generatedByS c.inScope
```

If a host has repair-accounting ledger entries that are themselves repair-typed audit entries, they should either be represented through the appropriate repair record family or given an explicit additional case tied to `S.Lambda_S.ledgerPolicy`. D5 should not invent a parallel "carried ledger" predicate.

### Complete declared history

The universal phrase "every repair-typed record entering T's audit" is only meaningful against a complete declared history. Otherwise the predicate could be satisfied by listing no bad records.

A D5 challenge history should therefore include:

```text
episodes : finite list or scoped sequence of ChallengeEpisode
repairAuditEntries : finite list of RepairTypedAuditEntry entering T.A
entryEpisode : each repair entry is attached to a declared episode/time
CompleteChallengeAuditHistory(S, H) : Prop
```

The completeness certificate says that, under the declared scope, the listed source-labeled `repairAuditEntries` are exactly the repair-typed records entering `T.A` for the challenge history, including the audit's declared `n0`, `sourceTag`, `generatedByS`, and `inScope` fields for each occurrence. This mirrors D3's `LegitimateStart` and carried-instrument inventory certificates: D5 does not derive completeness internally, but it refuses to assert closed-loop scope without it.

## 2. Definition

A declared challenge history `H` is **closed-loop for `S`** when:

1. **History/scope completeness.**

   ```text
   CompleteChallengeAuditHistory(S, H)
   ```

   The declared history is tied to `S.T.tau`, `S.T.StepInScope`, and `S.T.A`, and it enumerates all repair-typed records entering the audit apparatus under the declared scope.

2. **Repair-entry carriedness.**

   For every source-labeled repair-typed audit entry in the complete history:

   ```text
   forall e,
     e in H.repairAuditEntries ->
       RepairTypedAuditEntryCarried(S, e).
   ```

   In the three D4-native cases this expands to:

   ```text
   defect d c -> CarriedRecordAt S.defectRecordPolicy d c.n0 c.sourceTag c.generatedByS c.inScope
   move m c   -> CarriedRecordAt S.moveRecordPolicy m c.n0 c.sourceTag c.generatedByS c.inScope
   audit a c  -> CarriedRecordAt S.auditRecordPolicy a c.n0 c.sourceTag c.generatedByS c.inScope
   ```

3. **Source-policy admissibility.**

   The carriedness check is D3 carriedness checked against the audit entry's own declared classification fields. Therefore the entry's own source component must satisfy D3 `CarriedSource`: the source tag is `committed_state` or `audited_cell_records`, `generatedByS = true`, and `inScope = true`.

Thus:

```text
ClosedLoopScope(S, H) :=
  CompleteChallengeAuditHistory(S, H)
  and forall e in H.repairAuditEntries,
    RepairTypedAuditEntryCarried(S, e).
```

The parenthetical in THEOREMS.md is then literal: a theorist-supplied refinement is inadmissible because its audit entry fails the D3/D4 carriedness source policy, not because the prose disapproves of it. A repair package `R` that would refine `Q` to `Q vee R` under D1 is still inadmissible in a closed-loop history if the corresponding defect/move/audit entry's own declared `sourceTag` is `fallback`, `unknown`, or `contradictory`, if its own `generatedByS = false`, if its own `inScope = false`, or if `CarriedRecordAt` fails against the fixed D4 record policy.

This is deliberately stronger than checking `HasCarriedRecordEvidence` for the bare record value. `HasCarriedRecordEvidence` existentially says that some carried occurrence of the value exists. D5 needs the specific audit occurrence to be carried under its own declared source fields.

Minimal later-Lean declarations:

- `RepairEntryClass` carrying `n0`, `sourceTag`, `generatedByS`, and `inScope`.
- `RepairTypedAuditEntry` as a tagged sum over D4 defect, move, and audit records, each paired with its own `RepairEntryClass`.
- `RepairTypedAuditEntryCarried S e` by dispatch to D4 `CarriedRecordAt`.
- `ChallengeEpisode` as F2-style challenge data indexed along `S.T.tau`.
- `ChallengeHistory` with source-labeled `repairAuditEntries` and a completeness certificate.
- `ClosedLoopScope S H`.
- projection lemmas: a closed-loop history supplies carriedness for every listed repair-typed entry.
- exclusion lemmas: a listed fallback/non-carried audit occurrence contradicts `ClosedLoopScope`.

## 3. Proof Spine

D5 is a definition. The proof obligations are non-vacuity of the history interface, source-policy exclusion, and compatibility with D4 lawful repair steps.

### What is straightforward

If every repair entry in `H` is produced by a genuine D4 `ESystem.RepairStep`, then the host assembling `H` should record the same concrete classification data used when that step's carriedness was established:

```text
n0
sourceTag
generatedByS
inScope
CarriedRecordAt policy rho n0 sourceTag generatedByS inScope
```

for the defect, move, and audit entries. Those concrete proofs are exactly what D5 checks.

The direction from concrete D5 data to D4-style existential evidence is straightforward: from

```text
CarriedRecordAt policy rho n0 sourceTag generatedByS inScope
```

one can package `n0`, `sourceTag`, `generatedByS`, and `inScope` into a `CarriedRecordEvidence`, hence derive

```text
HasCarriedRecordEvidence policy rho.
```

The reverse direction is not what D5 should use. D4's `LawfulRepairStep.defectCarried`, `RepairMove.moveRecordCarried`, and `LawfulRepairStep.auditRecordCarried` are `HasCarriedRecordEvidence` facts, i.e. `Nonempty` existential evidence. After erasure into that Prop, D5 should not try to extract the concrete fields, and doing so would invite `Classical.choice`. Instead, a D5 `ChallengeHistory` records the fields as part of the audit entry before that information is erased.

Together with `CompleteChallengeAuditHistory(S, H)`, the per-entry concrete `CarriedRecordAt` checks imply `ClosedLoopScope(S, H)`.

The source-policy exclusion follows from D3. `CarriedRecordAt policy rho n0 sourceTag generatedByS inScope` unfolds to a D3 `CarriedRecord`, which includes `CarriedSource sourceTag generatedByS inScope`. D3 proves that fallback, unknown, contradictory, and the other non-admitted fine tags do not satisfy `CarriedSource`. Therefore a listed repair entry whose own declared source is fallback or a theorist edit cannot satisfy `RepairTypedAuditEntryCarried`.

Adversarial check: suppose two audit entries have the same record value `rho`. One entered as committed state and has a valid `CarriedRecordAt`; the other entered through a fallback source. The fallback entry cannot borrow the committed entry's proof, because D5 checks

```text
CarriedRecordAt policy rho n0_fallback FineSourceTag.fallback generatedByS inScope
```

using the fallback entry's own fields. This requires `CarriedSource FineSourceTag.fallback generatedByS inScope`, which D3 refutes. The same argument blocks `generatedByS = false` and `inScope = false`. Equal record values do not identify audit occurrences.

Under finite `repairAuditEntries` and decidable carriedness predicates, `ClosedLoopScope` is decidable as a finite all-records check plus the completeness certificate.

### The vacuity boundary

A complete history with zero repair-typed audit entries satisfies the universal carriedness clause vacuously. This is intentional but weak: it means "no external repair source appears in the declared audit history," not "the system can repair endogenously when challenged."

The load-bearing guard is the completeness certificate. If the history omits a fallback repair record that actually entered `T.A`, then `CompleteChallengeAuditHistory(S, H)` is false and D5 cannot be asserted. If no repair records entered the audit because no challenge bound or no repair was attempted, then closed-loop scope may hold vacuously; later laws such as E1 add recurrence, obstruction, and discharge hypotheses before claiming endogenous repair.

### What is deferred

D5 does not define the concrete challenge-class taxonomy, positive-density recurrence, obstruction reduction, or discharge measurement. Those are E1/E5-level obligations.

D5 also does not prove that the host's completeness certificate is honest. As in D3 and D4, completeness is certified input. Later toy-lab or E-law units must make the history/audit enumeration concrete enough to test.

## 4. Case Enumeration

- **Lawful D4 repair step:** a challenge episode produces a D4 `ESystem.RepairStep`; the history records the concrete `n0`, `sourceTag`, `generatedByS`, and `inScope` fields for its defect, move, and audit entries, and those entries satisfy `CarriedRecordAt`. If the history is complete, this episode satisfies D5.
- **D1 repair join with carried source:** a repair package `R` installs `Q |-> Q vee R`, and the audit entry for `R` has its own committed/audited source fields satisfying `CarriedRecordAt S.moveRecordPolicy ...`. This can be closed-loop.
- **D1 repair join supplied by theorist:** the same quotient operation is written into the audit with the same record value as a valid carried repair, but this occurrence has `sourceTag = fallback` or `generatedByS = false`. It is inadmissible under D5 because its own `CarriedRecordAt` check fails, even if another equal-valued occurrence is genuinely carried and even if it mathematically reduces `Delta`.
- **Off-kernel repair:** a repair-like transition not realized by `S.T.suppK` fails D4 lawful-repair status. If it enters the audit as repair-typed but is not carried, D5 fails; if it is hidden from the history, the completeness certificate fails.
- **No repair entries:** a complete history with no repair-typed entries is closed-loop vacuously. This is only a scope hygiene result, not evidence of repair capacity.
- **Challenge with no repair:** a binding challenge may recur while no repair record enters the audit. D5 can still hold; E1/E5 then decide whether the system is stressed, collapsing, or slack under their additional hypotheses.
- **Non-repair annotation:** a theorist annotation that is not repair-typed is outside D5's universal clause. It may still matter to other audit laws, but it is not a repair source.
- **Incomplete audit list:** a history that lists only source-labeled carried repairs while omitting an external/fallback repair occurrence is not closed-loop because `CompleteChallengeAuditHistory` is missing or false.
- **Ledger-only bookkeeping:** a budget/status ledger entry is already governed by D4 `Lambda_S`. It is D5-relevant only when the host classifies it as a repair-typed audit entry or ties it to a repair record.

## 5. Interaction Status

D5 depends on D4 and sharpens D3's role inside a challenge history.

- **D4 E-system:** D5 is a predicate over a D4 `ESystem` plus a declared challenge/audit history. It uses `S.T.A` as the audit surface, `S.T.tau` / `StepInScope` as the declared history base, and D4's fixed record policies for defect, move, and audit records. Unlike D4's existential `HasCarriedRecordEvidence` fields, D5 checks the concrete source-labeled audit occurrence with `CarriedRecordAt`.
- **D3 carriedness:** D5 does not redefine carriedness. It dispatches every repair-typed audit occurrence to D3 carried-record evidence through D4's fixed policies and the occurrence's own declared fields. The parenthetical about theorist-supplied refinements is exactly D3 `CarriedSource` discipline.
- **D1 repair join:** D5 does not change the operation `Q |-> Q vee R`. It decides whether a repair package/readout used in such an operation is an admissible endogenous source in the challenge history.
- **FIV F2:** D5's challenge episodes are grounded in F2 split-pair obstruction data. D5 does not restate F2; it governs the provenance of repair records created when such obstructions are challenged.
- **E1 Internalization:** THEOREMS.md's E1 explicitly assumes an E-system "under closed-loop scope (D5)." D5 supplies the no-external-repair-source hypothesis that E1 needs before inferring carried repair records from persistence-with-discharge.
- **E5 Reclosure Collapse:** E5 uses admissible carried moves in its collapse taxonomy. D5 supplies the scope guard that prevents theorist repairs from being counted as admissible carried moves.

Under the anti-reductionism discipline, D5 is not "just" D3 applied pointwise and not "just" D4 lawful steps. It records a history-level governance condition: the complete audit history for a challenge class admits no external repair source.

## 6. Nonclaims

- D5 does not prove that challenges recur, bind, or occur at positive density.
- D5 does not prove that any split-pair obstruction is reduced.
- D5 does not prove that a system has repair capacity. A complete history with no repair-typed entries can be closed-loop vacuously.
- D5 does not prove that all records in `T.A` are carried; it only governs source-labeled repair-typed audit occurrences under the declared challenge scope.
- D5 does not prove that `CompleteChallengeAuditHistory` is honest. It is a certified input, like D3's `LegitimateStart` and D4's inventory-completeness certificates, and it must cover the source fields attached to each audit occurrence, not only the bare record values.
- D5 does not extract concrete source fields from D4's already-erased `HasCarriedRecordEvidence` proofs. The concrete `n0`, `sourceTag`, `generatedByS`, and `inScope` fields must be supplied by the challenge-history entry itself.
- D5 does not make a fallback/theorist repair false or mathematically useless. It only makes it inadmissible as an endogenous repair source under closed-loop scope.
- D5 does not claim that D1 source refinement is always the correct repair path; F2 also allows target coarsening, and D5 applies to repair-typed records regardless of repair shape.
- D5 does not prove D4 `Detects`, `GateAllows`, `ReAudits`, or `AdmissibleMove` are honestly instantiated.
- D5 does not introduce biological or life-sciences content.
