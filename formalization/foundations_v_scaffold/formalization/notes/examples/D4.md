# D4 - Endogenous Closure System, E-System

**Source text:** THEOREMS.md §1.2, D4.  
**Target Lean module:** `SixBirdsFoundationsV.Definitional.ESystem`.  
**Grounding:** D1 supplies repair joins/refinement operations, D2 supplies declared surplus/residual ledger discipline, D3 supplies carried records and carried instruments, FIII supplies `Primitive.P1`--`Primitive.P6` and instrument/status vocabulary, and FIV supplies the formed-package/formed-closure discipline. Reflexive SBT supplies the analyst-side audit loop that D4 internalizes only when the loop's records and moves are carried by the system.

## 1. Setup

D4 defines the first composite Foundations-V object. An E-system is not just a formed package plus extra labels; it is a formed package whose audit, ledger, and repair loop are carried on the same carrier and are realized by the system's own transition support.

### Mathlib / ClosureLadder boundary

Foundations I's local Lean project lives at `six-birds-theory/formal` and its `lakefile.toml` requires Mathlib:

```toml
[[require]]
name = "mathlib"
scope = "leanprover-community"
rev = "v4.26.0"
```

Its `ClosureLadder` modules use Mathlib closure operators, complete lattices, quotient packaging, and idempotent endomaps. That is real infrastructure, but it is not necessary for D4's definition. D4 can state the E-system tuple parametrically over:

```text
Z                         carrier state type
suppK : Z -> Z -> Prop    own transition support / kernel support
LegitimateStart            declared start certificate for the shared history
tau : Nat -> Z             shared declared trajectory / history
StepInScope : Nat -> Prop  declared in-scope steps for the shared history
nStart : Nat               shared start index for D3 carriedness checks
f                         update/readout apparatus, left abstract
Sigma_f                   declared closure rule family, left abstract
E                         residual / defect / status space, left abstract
A                         access/audit apparatus, left abstract
FormedPackage(T)          certified formed-package predicate
```

This preserves the current Mathlib-free Foundations-V Lean style. The later Lean unit should not vendor Foundations I / ClosureLadder merely to define D4. If a later theorem needs concrete closure-operator laws from ClosureLadder, that is a separate infrastructure decision because it would introduce the first Mathlib dependency into this repo.

### Formed package

FIV gives the operative meaning of "formed" rather than treating it as informal well-formedness.

FIV Definition `def:closure-formation` says a closure formation is the passage from initial data to the object obtained by closing that data under declared closure rules; a formed closure is the completed object relative to those rules; and a closure-of-record is a formed closure together with an audit record of the closure data used to form it.

FIV's stability axis then specializes this to formed packages:

- F6 No-Needles uses a formed stability package: a closure carrier with inherited closure apparatus, quotient discipline, audit ledger, and layer-dissolving membrane.
- F9 No Unstatused Residual says a formed package has a native residual registry and a typed-status classifier; every native residual has a declared typed status, and the classifier is single-valued.

For D4, `FormedPackage(T)` should therefore mean at least:

```text
formed_closure(T)                 T is completed under declared closure rules
closure_of_record(T)              the closure data used to form T is audited
quotient_discipline(T)            the current quotient/readout discipline is declared
native_residual_coverage(T)       every native residual has a typed status record
status_classifier_single_valued(T) residual/status classification is single-valued
```

The Lean target should keep this as a certified predicate or small structure of predicates. D4 does not need to reconstruct FIV's entire formed-package theory.

### Carried components

D4 should reuse D3 directly.

- `I_S` is a D3 `CarriedInstrument`, including its complete-inventory certificate for the instrument's visibility, threshold, and audit/check-rule records.
- `Lambda_S` is a carried ledger: a complete declared family of budget, price, statused-residual, and repair-accounting records, each represented as a D3 `CarriedRecord` over the carrier `Z` using one fixed ledger-record coordinate/readout policy.
- Defect, move, and audit records consumed or emitted by the repair generator are also D3 `CarriedRecord`s, each checked against its fixed family coordinate/readout policy and the shared declared trajectory/scope data of `T`. This avoids inventing a parallel carriedness predicate and makes "carried repair generator" checkable rather than philosophical.

### Repair sorts

The vendored FIII Lean has:

```lean
inductive Primitive where
  | P1 | P2 | P3 | P4 | P5 | P6
```

D4's repair generator ranges over P1--P5:

```text
P1 rewrite
P2 gate
P3 route-mismatch / holonomy reconciliation
P4 refinement / staging / gluing
P5 packaging / completion / objecthood
```

`P6` is audit/accounting. In D4, audit/accounting is the job of `I_S` and the ledger, not the repair generator. The later Lean target should encode repair moves as a subtype such as:

```text
RepairSort := { p : SixBirdsIII.Primitive // p ≠ SixBirdsIII.Primitive.P6 }
```

rather than using the full primitive type and relying on prose to exclude P6.

## 2. Definition

An **E-system** is a tuple

```text
S = (T, I_S, Lambda_S, R_S)
```

with the following data and certificates.

### 2.1 Formed carrier package

`T = (Z, f, Sigma_f, E, A)` is a formed package over carrier `Z`.

For Lean, this should be a parametric structure:

```text
TheoryPackage :=
  Z                         : Type
  suppK                     : Z -> Z -> Prop
  LegitimateStart           : (Nat -> Z) -> Nat -> Prop
  tau                       : Nat -> Z
  StepInScope               : Nat -> Prop
  nStart                    : Nat
  f                         : FData
  Sigma_f                   : RuleFamily
  E                         : ResidualFamily
  A                         : AuditAccessData
  formed                    : FormedPackage(T)
```

The exact types of `FData`, `RuleFamily`, `ResidualFamily`, and `AuditAccessData` are host-specific parameters. The load-bearing point for D4 is the `formed` certificate, not a particular Foundations I implementation.

### 2.2 Carried instrument

`I_S` is an active D3 carried instrument over `Z`. Its visibility, threshold, and audit/check-rule records must be D3-carried records, and its record lists must have a certified complete-inventory witness. `I_S` is not inert: the same value that carries the D3 `CarriedInstrument` proof also supplies the detection, gate, and re-audit predicates that constrain `R_S`.

The abstract predicates are:

```text
Detects(I_S, z, d)          I_S detects defect record d at state z
GateAllows(I_S, z, d, m)    I_S permits repair move m for d at z
ReAudits(I_S, z, m, z', a)  I_S re-audits the transition and emits audit/status record a
```

Each detection and audit/status record used here is a D3 `CarriedRecord`.

### 2.3 Carried ledger

`Lambda_S` is a carried ledger. It contains budgets, prices, statused residuals, capacity charges, and repair accounting as state coordinates of `Z`, not as theorist-side annotations.

A Lean target should model it as:

```text
LedgerEntry                 entry type
ledgerPolicy                fixed coordinate/readout policy for ledger entries
ledgerEntries : List LedgerEntry
ledgerComplete : CompleteLedgerInventory(T, ledgerEntries)
ledgerCarried : forall entry in ledgerEntries, CarriedRecord(T, ledgerPolicy, entry)
```

`CompleteLedgerInventory` should be a certified input in the same style as D3's `recordsAreCompleteInventory`. D4 should not infer ledger completeness from a list being present.

### 2.4 Carried repair generator

`R_S` maps carried defect records to admissible P1--P5 moves realized by the system's own transition support and gated by `I_S`.

An admissible repair move contains:

```text
sort : RepairSort                  -- P1--P5, not P6
payload : MovePayload              -- host-specific move data
moveRecord : MoveRecord            -- host-specific move/audit datum
moveRecordCarried : CarriedRecord(T, moveRecordPolicy, moveRecord)
budgetLine : LedgerEntry           -- the move is charged/statused in Lambda_S
```

The generator is lawful only with the following certificates:

```text
defectCarried(d)                   -- checked against the fixed defect policy
Detects(I_S, z, d)
GateAllows(I_S, z, d, m)
AdmissibleMove(T, Lambda_S, z, d, m)
suppK z z'                         -- the move is realized as an own-kernel transition
ReAudits(I_S, z, m, z', a)
auditRecordCarried(a)              -- checked against the fixed audit policy
```

Thus the active D4 loop is:

```text
defect detected by I_S
  -> move emitted by R_S
  -> move realized by suppK
  -> re-audit by I_S
  -> ledger/status update in Lambda_S
```

The instrument must constrain both ends of the loop: a defect record not detected by `I_S` cannot trigger a lawful `R_S` move, and a move not re-audited by `I_S` is not a completed endogenous repair step.

## 3. Proof Spine

D4 is a definition. The proof obligations are composition, non-vacuity guards, and clear dependency boundaries.

### What is straightforward

Given the accepted D1--D3 Lean surface, the later D4 Lean unit can define:

- a parametric `TheoryPackage` with carrier `Z`, kernel support `suppK`, abstract closure/audit fields, and a `FormedPackage` certificate;
- a `RepairSort` subtype excluding `SixBirdsIII.Primitive.P6`;
- ledger and defect record predicates using D3 `CarriedRecord`;
- a carried-instrument field using D3 `CarriedInstrument`, bundled with the detection, gate, and re-audit predicates it supplies;
- a repair-generator predicate requiring detection, gate permission, own-kernel transition, and re-audit.

The main well-definedness checks are direct:

- P6 exclusion follows from the `RepairSort` subtype.
- Carried ledger entries, defect records, move records, and audit records reduce to D3 `CarriedRecord` under fixed family coordinate/readout policies and the shared declared trajectory/scope data of `T`.
- Empty or cherry-picked instrument record lists do not suffice because D3 `CarriedInstrument` already requires a complete-inventory certificate.
- A repair emitted by `R_S` is not endogenous unless it is both gated by `I_S` and realized by `suppK`.

The Lean anchor must not allow per-record ad hoc carriedness witnesses. The system-level data `LegitimateStart`, `tau`, `StepInScope`, and `nStart` are fixed in `T`, and each record family has one fixed coordinate/readout policy. A particular record instance supplies only its value, read-off time `n0`, source tag, generated-by-system flag, and in-scope flag. If an instantiation chooses `n0 = nStart` for every record, the D3 trace interval is empty for those records; that is the same certified-start/scope-window residual D3 already accepts, now shared at E-system scope rather than re-created per record. It is not a new logical escape hatch, but concrete E-law instances must justify the declared history and read-off times.

Under finite declared record lists and decidable component predicates, the E-system predicate is decidable as a finite conjunction of D3-style carriedness checks, complete-inventory certificates, and transition/gate/re-audit predicates.

### What is deliberately deferred

D4 does not require a Mathlib/ClosureLadder dependency for its Lean anchor. The formed-package component can be a certified predicate. If a later theorem needs to prove closure-operator facts, complete-lattice facts, or closure-ladder monotonicity from Foundations I's concrete Lean, that must be an explicit infrastructure decision before the Lean unit imports or vendors ClosureLadder.

D4 also does not prove that every detected defect is eventually repaired, that repairs reduce D2 surplus, or that the reflexive loop converges. Those are E-law obligations, not part of the E-system definition.

## 4. Case Enumeration

- **Valid E-system:** a formed package whose carried instrument detects a carried defect, gates a P1--P5 move, realizes it through `suppK`, re-audits the result, and records the cost/status in a carried ledger.
- **Unformed package:** a carrier with records and moves but no formed-closure / closure-of-record / residual-coverage certificate is not an E-system.
- **Instrument listed but inert:** an instrument field that does not constrain detection, gating, and re-audit is not enough; `I_S` must bundle the carried-instrument proof with the predicates used by `R_S`.
- **Uncarried ledger:** budgets or residuals maintained in a theorist notebook are not `Lambda_S`.
- **Ad hoc carriedness witness:** a record cannot become carried by choosing a fresh constant readout and empty trace for that record alone; carriedness must be checked through the system's fixed trajectory/scope data and the record family's fixed coordinate/readout policy.
- **Fallback defect record:** a defect with fallback, unknown, contradictory, or non-D3 fine source does not trigger a carried repair generator.
- **P6 as repair:** a move whose sort is P6 is not an `R_S` repair move. Audit/accounting belongs to `I_S` and `Lambda_S`.
- **Off-kernel repair:** a proposed repair not witnessed by `suppK z z'` is an observer intervention, not an endogenous repair transition.
- **Ungated repair:** a move emitted without `GateAllows(I_S, z, d, m)` fails D4 even if it is mathematically useful.
- **No re-audit:** a move that changes the carrier but is not re-audited by `I_S` is an incomplete loop, not a completed E-system repair step.
- **Analyst-side Reflexive SBT loop:** an external Python loop that audits artifacts and applies meta-moves is not yet an E-system. It becomes an E-system instance only when the artifacts, audits, moves, and ledgers are carried by the carrier and realized by `suppK`.

## 5. Interaction Status

D4 composes D1--D3 rather than reducing them.

- **D1:** P4/refinement moves may use repair joins of the form `Q |-> Q vee R`, but D4 adds the requirement that the repair package/readout `R` be carried and kernel-realized.
- **D2:** `Lambda_S` carries closure deficits, adequacy residuals, prices, budgets, and statused residuals. D4 does not assert surplus reduction; it only supplies the endogenous ledger on which later E-laws state reduction claims.
- **D3:** `I_S`, ledger entries, defect records, move records, and audit records should all reuse D3 carriedness. This is the clean way to avoid parallel source-of-truth machinery.
- **FIII:** D4 imports the primitive sort vocabulary and instrument/status apparatus. It narrows `R_S` to P1--P5 because P6 is audit/accounting.
- **FIV formed packages:** D4 relies on FIV's formed-closure and residual-coverage discipline. It should cite formed package as a certified predicate, not redefine the whole FIV apparatus.
- **Reflexive SBT:** the Reflexive SBT paper describes an analyst-side loop: audit artifacts, run closure tests, suggest primitive firings, apply meta-moves, and re-audit. The paper explicitly presents this as a bridge asset, not a universal theorem. D4's claim is accurate only with this scope: it internalizes the loop onto the carrier when the audit records, move records, ledger, and transitions are D3-carried and own-kernel-realized.

Under the anti-reductionism discipline, D4 is not "just" FIII instruments, FIV formed packages, or Reflexive SBT relabeled. It maps their interfaces and adds the new carried/internality condition that makes the loop endogenous to a social, economic, or cognitive carrier.

## 6. Nonclaims

- D4 does not require vendoring Foundations I / ClosureLadder or adding Mathlib for its own Lean definition. That would be a separate infrastructure decision for later closure-operator theorems.
- D4 does not define a concrete closure operator, complete lattice, or theory-package implementation.
- D4 does not prove that `FormedPackage(T)` holds for any given carrier; it treats formedness as a certified input grounded in FIV.
- D4 does not prove that `CompleteLedgerInventory`, instrument-record completeness certificates, fixed record-family policies, or the shared `LegitimateStart`/trajectory/scope-window certificates are honest; they are certified inputs, like D3's `LegitimateStart`.
- D4 does not claim every carried instrument is part of an E-system. The instrument must detect, gate, and re-audit the repair loop.
- D4 does not prove that `Detects`, `GateAllows`, `ReAudits`, or `AdmissibleMove` are honestly instantiated. It only requires them as explicit predicates bundled with the active carried instrument or supplied as certified admissibility data.
- D4 does not prove that `suppK z z'` means the repair payload caused or constituted the transition. `suppK` proves only that the transition lies in the kernel support; payload-realization semantics must come from `AdmissibleMove`, `GateAllows`, or a later `RealizesMove`-style predicate.
- D4 does not claim every carried ledger is adequate, truthful, noncaptured, or surplus-reducing.
- D4 does not claim every defect has a repair, every repair succeeds, or every repair reduces D2 surplus.
- D4 does not make P6 a repair-generator move; P6 remains audit/accounting.
- D4 does not turn the Reflexive SBT loop into a universal convergence theorem. It only states when that audit/move/re-audit loop is carried by the system's own carrier and kernel.
- D4 does not introduce biological or life-sciences content.
