This note is the six-part deep-dive split out from `THEOREMS.md`'s compressed G3 catalog entry, per

## 1. Setup → Lean target

`THEOREMS.md` §G3 "1. Setup" (finite run prefix `s_0 -> ... -> s_n`, declared actual cost `a_i`, potential
`Phi: S -> Q_{>=0}`, amortized cost `a_hat_i = a_i + Phi(s_i) - Phi(s_{i-1})`) is mechanized in `lean/
SixBirdsFoundationsVI/Laws/G3AmortizedCurrency.lean` as: `RunPrefix S := List (Int × S)`, `FinalState`,
`ActualCostSum`, `AmortizedCostAt`/`AmortizedCostSum` (threading the previous state through the list,
mirroring G8's `RunCounter` recursion style), `NonnegativePotential`/`NonnegativeActualCosts`,
`AmortizedCostList`/`AllLe` (for the uniform-bound hypothesis), `ScaleCost` (hand-rolled repeated-addition
`n*B`).

**Type choice: `Int`, not `Q_{≥0}`.** Honestly disclosed in the file's own docstring: Mathlib-free core
`Rat` lacks the algebra-lemma names needed for a clean proof, and two of the three named calibrations
(binary counter, dynamic array) are integer-valued anyway. The one calibration this can't reach without
revisiting the choice is splay trees' logarithmic potential (Layer Instantiation 3) — flagged here
explicitly; the gate note records integer-valued scope and the splay-tree skip, not silently dropped.

**No Lean imports.** Like G2 and G8, standalone — but this one has history: the first draft included
`import Std` (this project's first-ever non-project import, and a real process deviation — see §7).

## 2. Theorem → Lean target

`telescoping_identity` (the exact identity), `telescoping_bound` (the inequality, using
`Phi(s_n) ≥ 0`), `amortized_sum_le_scale` (per-step bound `B` implies sum `≤ n·B`, via `ScaleCost`),

## 3. Proof spine → Lean target

The telescoping expansion (cancel adjacent `Phi` terms) is `telescoping_identity`'s inductive proof —
substituting the IH into the unfolded goal cancels every `Phi s1`/`Phi s0`/`Phi(FinalState...)` term
pair, leaving exactly the actual-cost sum (hand-verified by the manager, not just kernel-checked). The
binary-counter and dynamic-array worked checks are lab/instantiation content (§4), not part of the
abstract law.

## 4. Case enumeration → deliberately not mechanized

Unlike G8 (two concrete separating-witness proofs), G3's Case Enumeration (prepaid / borrow-and-repay /
insolvent) classifies **a declared run family plus an audited `Phi`** as one combined object — per
Reviewer's sharpened point during the Lean review: even the easy (a)/(b) dichotomy ("is `Phi`
nonincreasing everywhere, or does it increase somewhere") would only capture a per-prefix property, not
the prose's actual object (an audit record over a whole *family* of runs). The current Lean file works
over individual finite prefixes, not run families, so mechanizing even the easy half wouldn't actually
represent the table. Recorded as a deliberate scope boundary, not an oversight.

- **Local example (G3-L1)**: `lab/foundations_vi_lab/g03_currency/{ledger,binary_counter,dynamic_array,
  run}.py` implements the binary-counter (`Phi=popcount`) and dynamic-array (`Phi=max(0,2·size-capacity)`)
  calibrations exactly, verifying the telescoping identity and claimed cost bounds over 1000 seeded
  operations each. Both worked examples from `THEOREMS.md`'s Proof Spine are reproduced exactly
  (hand-traced by the manager against the actual code). Splay trees skipped per the design spec's
  explicit "optional... cite instead."

## 7. Prose-to-Lean / process fidelity issues found during mechanization

1. **`import Std` in the first Lean draft.** The first submission opened with `import Std`, the first
   non-project import anywhere in this repo's Lean tree — a real deviation from the established
   zero-import, Mathlib-free convention. Investigation: `Std` resolves because it's bundled directly with
   the pinned toolchain (`leanprover/lean4:v4.28.0`, 394 files: `Std.Data`/`Do`/`Sat`/`Sync`/`Time`/
   `Tactic`/`Internal`/`Net`), so `lake build` succeeded silently — there was no dependency-graph signal
   to catch it. Confirmed by `grep "Std\."` (zero references) and by empirically rebuilding without the
   line (identical success) that it was pure dead code. Removed. Recorded here as a standing checklist
   item for future Lean packets in this project: grep every new Lean file's `import` lines explicitly —
   a clean `lake build` is not evidence a file honors the zero-import convention, since a bundled-with-
   the-toolchain library can resolve silently without any dependency-graph signal.
2. No mathematical fidelity issues were found in this law's Lean content (contrast with G8, which needed
   two real bug fixes). The telescoping proof was correct on first mathematical submission; the only
   issue was the process deviation above.
